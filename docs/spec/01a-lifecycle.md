# Lifecycle states and transition table (problem level)

This file is the **single owner** of the problem-level lifecycle (lifecycle v2, D-72, ADR 0015): the problem state classes, the transition table (T00 to T22), the old to new transition map, and the rules that apply to them. The stage-level lifecycle (the stage plan, stage states, stage gating and per-stage contribution rules) is owned by `01b-stages.md`. Link here for the table; never copy it elsewhere. `01-slice-1-brief.md` owns the scope and defaults, the preparation and volunteer review flow, the moderation decision fields (its section 5), the contribution-type enum and the entity list. The structured fields each transition requires are defined by the content schemas in the policy pack (`05-lifecycle-participation.md`, D-58); the "required fields" column below is the minimum the server enforces.

## 4.1 State classes

| State | Class | Who sees it |
|---|---|---|
| `draft` | Pre-publication | the poster only |
| `in_review` | Pre-publication | the poster, and opted-in volunteers with personal data masked. Never public |
| `needs_revision` | Pre-publication | the poster only |
| `held` | Pre-publication (fail closed) | the poster only |
| `rejected` | Pre-publication, terminal, appealable | the poster only |
| `active` | Working (public) | everyone. The stage plan is running |
| `paused`, `stuck` | Resting (public, not terminal) | everyone |
| `solved`, `closed`, `redirected` | Terminal (public) | everyone |
| `withdrawn` | Terminal. Public after publication (T18, `OWN-1`), private before | depends on timing |

Notes on the model:

- The initiator is called the **poster** while preparing. After publication the poster is the provisional steward (`04-roles-stewardship.md`).
- `active` is the only working state. What used to be separate working states (gathering facts, developing solutions, choosing, in progress, checking) is now the stage plan (`01b-stages.md`). The old sequence survives as the optional template `classic-5`.
- `automated_review` is a synchronous check inside T01, not a state. A hard failure keeps the problem in `draft` with field hints and creates no moderation decision.
- `held` is the fail-closed state (`PUB-FAILCLOSED-1`): a moderation run could not complete. It is private and never reaches `active`. It remembers its `resume_state`.
- `appealed` is not a state. An appeal attaches to a moderation decision (brief section 5).
- `investigation_needed` is a **derived flag**, true when the strongest evidence tier on a published problem is below the investigation threshold (Constitution III.4, `EVIDENCE-TIERS`).
- `paused` is not terminal: it requires a reason and a resume condition. `stuck` means documented effort has hit a blocker; it is the public "accountable unresolved record". A single blocked stage is a stage state (`blocked`, `01b-stages.md`). The problem becomes `stuck` only when no remaining required stage can proceed.
- A terminal or resting state reopens only through T20 or T21 (re-resolution, D-59). `withdrawn` and `rejected` never reopen by re-resolution.
- Invalid transitions fail atomically. Every transition writes a `problem_event` (actor, time, from, to, reason, evidence ids) in the same transaction.
- "Proposes / decides": the poster (or steward) records a pending transition; the moderation run applies the policy and confirms or declines it, citing rule ids. No human confirms an ordinary transition. `escalate_human` (emergency, crisis, law enforcement) goes to the logged emergency/legal lane.
- Decision points are the `DP-*` ids in the table (catalog: `docs/design/ai/decision-points.md`). New in v2: `DP-SOURCE-TRUST` (are the cited URIs trusted and authentic), `DP-CRITERIA` (are the acceptance criteria measurable, lawful and fitting), `DP-STAGE-PLAN` (is the plan a well-formed DAG, does every stage have criteria; it runs on submit and on every plan-change proposal), `DP-PUBLISH` (the publication decision, which aggregates the other DPs plus any recommendations still open), `DP-STAGE-RESOLUTION` (has a stage met its criteria; `01b-stages.md`). `DP-VERIFICATION` now judges only the final `solved` state against the final acceptance criteria. `DP-STAGE` (the old stage transition meaning) is retired. Outcomes: `publish`, `needs_revision`, `reject`, `route_external`, `hold` (fail closed), `escalate_human`.

## 4.4 Rules that apply to the table

- **Archive (`ARCHIVE-1`).** Every terminal transition after publication (T15 to T18) and T13 (`stuck`) triggers `DP-ARCHIVE`, which builds the public, personal-data-stripped archive record with failed paths and challenges. Owner of the record: `24-archive-reuse.md`.
- **Preparation and review.** A problem cannot leave `draft` without final acceptance criteria (`CRITERIA-1`). Volunteer review is required before publication, its content is never public and personal data is masked (`REVIEW-1`). Every recommendation gets an accept or decline from the poster with a reason (`RECO-1`). Flow and entities: `01-slice-1-brief.md` section 4.
- **Withdrawal after publication** (T18) only while nobody else has an accepted contribution. After that the poster can only tombstone their own text (`tombstoned_at`) or ask for closure with reason "initiator request" (T16). The poster owns nothing (`OWN-1`).
- **Solved is final-criteria only.** `solved` needs every required stage `resolved` or `skipped` and `DP-VERIFICATION` meeting the final acceptance criteria. Completed tasks or a promise alone never qualify (`VERIFY-1`). A "not met" result changes no state and names the unmet criteria.
- **Pause review:** when the review date passes, the system queues a re-check by the moderation run and notifies the poster. It never changes state by itself.
- **Appeals** change state only through the effects in brief section 5.
- **Re-resolution (T20, T21, `RERESOLVE-1`):** a policy-pack or legal-corpus change queues a review of past solved, closed, redirected and stuck problems and their decision records under the new version, and re-runs `DP-STAGE-RESOLUTION` on resolved stages whose evidence rule changed. It reopens only when the conclusion changes and the feasibility check passes; otherwise it writes a record and changes no state. It is never silent and never deletes history. A reopened problem that again reaches a terminal state gets a new archive record and keeps the old one.
- **Legal layers:** `DP-LEGALITY` and every legal check apply the cumulative layer stack L0 to L6 (Constitution I.2, `LEGAL-STACK-1`). Where local law forbids discussing a topic at all, T05 rejects with the legal basis logged (`TOPIC-FORBIDDEN-1`) and nothing is published in that jurisdiction. Where only a solution is illegal, the stage becomes `blocked` and, when nothing else can proceed, T13 applies: `stuck` (legally blocked), citing the layer and source.
- **Re-moderation after a policy change** can flip an outcome on a published problem. It never removes silently: the page shows "re-reviewed under policy vX", the reason and an appeal path (`REMOD-NOTICE-1`).
- Public labels are the exact chip text; explanations appear on the problem page and in the email. Labels never use red. Stage chips are in `01b-stages.md`.
