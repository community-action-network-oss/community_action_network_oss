# 03 Pick work

Work is split into units of about an hour, described in `plans/`. Each unit file states the goal, the steps, the acceptance list and the verify commands.

## Find a unit

1. Start with [good-first-units.md](../contributing/good-first-units.md): ten or fewer units that need no database and no deep spec read. It is generated by `node scripts/sync-good-first.mjs`; how units are chosen is explained in [docs/contributing/README.md](../contributing/README.md).
2. Want more? Browse the plan folders in `plans/` (index: [plans/00-ROOT.md](../../plans/00-ROOT.md)). The format is in [plans/FORMAT.md](../../plans/FORMAT.md).
3. Not code? Try an open question: [docs/open-questions](../open-questions/README.md).

Read a unit's `status` line before claiming it. Maintainers own that field; never edit it.

## Not good first

- **Founder-gated units** (`founder_gate: true`). Spike units such as the zero-knowledge location proof are in this group.
- **Units that need real devices**, such as phone testing or push notifications.
- Units with `needs` set to `docker`, `db` or `mail` are fine but slower to set up; check them against your setup.

These are not listed in the good-first index on purpose.

## How to claim

1. Open a task-claim issue (form in [.github/ISSUE_TEMPLATE](../../.github/ISSUE_TEMPLATE/task-claim.yml)) that cites the unit id, for example `13-u18`.
2. One person per unit at a time. A maintainer confirms the claim in the issue.
3. Work on a branch and open a pull request that cites the unit id.

If you stop, say so in the issue so someone else can take it. The project has no stated review capacity, so please do not plan around a reply time.
