# Contributing by unit

CAN work is split into small units described in `plans/`. [good-first-units.md](good-first-units.md) lists ten or fewer that you can finish in about an hour without a database or a deep spec read. It is generated by `node scripts/sync-good-first.mjs`; `--check` fails when it is stale.

## How units are chosen

A unit is listed when all of these hold:

- it is not founder-gated and has no `needs`;
- its estimate is one hour or less;
- it is not tagged `needs-context`.

The tag `good-first` forces a unit in. Two data-only units are also forced in by the script (the `FORCED` list), because domain experts and people who can read law can do them without writing code: 13-u18 (synthetic archive eval records and queries) and 10-u67 (the second synthetic jurisdiction). Forced units come first, then the rest by priority.

The list does not show status, so it never goes stale while work moves. Open the unit file and read its `status` line before claiming.

## How to claim a unit

1. Open an issue citing the unit id (for example `13-u18`).
2. One person per unit at a time. A maintainer confirms the claim in the issue.
3. Work on a branch and open a pull request that cites the unit id and runs `bash scripts/verify-all.sh`.

## What review to expect

A maintainer checks the unit's acceptance list, the verify commands and the decisions in `DECISIONS.md`. Expect a reply within a few days and small change requests.

## Status

Only maintainers change a unit's `status`. Do not edit it in your pull request.

## AI disclosure

If an AI tool wrote or shaped any part of your change, say so in the pull request. The full rule is in [docs/spec/22-ai-contribution-policy.md](../spec/22-ai-contribution-policy.md).
